Tests first, a person at every gate.

greenfield-pipeline is a plugin for Claude Code. It takes a software idea from scattered sources to a verified build and a handover pack, and it assumes no company, industry or stack.

It ships a command-line engine (gp), nine skills, six worker agents with limited tools, and a hook that pauses risky tool calls until the owner decides.

route

Six parts, one project

The deliver skill reads the project's files, picks the next unblocked item and runs the part it needs, until nothing is left or everything left waits on a person.

  1. plate sources to a canonical requirement

    Briefs, notes and replies are plated into one file, greenfield/requirements/<name>.canonical.yaml: surfaces, glossary, confirmed examples, data classes, regulated regimes. The items it demands are raised for a person.

    skill: plate

  2. shape design before any code

    An architecture note and interface contracts are written and the stack is decided, so there is a surface to test before anything is built.

    skill: shape. output: design/architecture.md, design/contracts/

  3. design one reviewed suite per acceptance criterion

    For each acceptance criterion (AC) a YAML suite is written, tracer case first, then clauses, negatives and edges. Every version waits for an independent review.

    gus writes, rex reviews

  4. build test-first, one AC at a time

    The software is built in the declared product repo against a suite that has already been seen to fail. Each build is recorded against a clean commit.

    ed builds

  5. verify run, judge, score, review

    The suites run through drivers (http, cli, manual). Rule checks are judged against the transcript by someone who has not seen the builder's notes. gp score combines the judgments, and every full run gets a review, whatever its result.

    eve runs, tim judges, rex reviews

  6. handover documents for the sponsor, drafted locally

    Eight markdown documents are generated from gp handover-data, including a limits page: what stayed unproven, which doubles stood in for real services, which assumptions are open. The certificate is left unsigned.

    dora drafts. never signs, sends or uploads

Two more skills sit beside the route. catchup lists what waits on the owner, decisions made since the last look, and the flags rex raised. retro proposes small changes to the project's pack and leaves it no larger than before; it never edits the plugin.

states

Red before green

Nothing is stored as "done". Each AC's state is derived from the project's files every time you ask (gp acs). Pick a state to see what it means and what moves an AC out of it.

the path, in order

two states override the path

no-suite

The AC has no acceptance suite yet.

Moves on when: the design part writes one, tracer case first.

in-review

A suite exists, but one of two things is missing: rex has not approved this version of it, or the owner has not accepted it.

Moves on when: rex approves the version and the owner accepts it at that file's hash.

ready

The suite is approved and accepted, and no run of that exact suite exists yet.

Moves on when: the first run happens. That run is expected to fail, before the build exists.

red

The latest run of this suite failed on this AC.

Moves on when: the build part fixes it, records the build, and the suite runs again.

green

The latest run passes, but done is still blocked by at least one of these:

  • no full run of this suite yet
  • the latest full run is not a pass
  • the run is not on the current build
  • rex has not reviewed that run
  • the AC was never seen red before its first green
  • the baseline is not approved

gp acs names which of these is holding each AC.

done

Every condition holds at once:

  • the suite is reviewed by rex and accepted by the owner at that file's hash
  • a full run of exactly that suite, on the current build, passes
  • rex has reviewed that run
  • the AC was seen red before its first green
  • the baseline is approved
  • no assumption is open

A green verdict means the accepted suites passed on one build. It does not prove quality outside what they check.

assumed

An assumption on this AC is open. This state wins over every other one until the assumption is closed. An assumption's source is its tag, and a source of memory, or a public finding nobody confirmed, never closes one.

Moves on when: a person confirms the assumption from a source that can close it.

stale

The AC, or a contract the suite copies from, changed after the suite was written. A stale suite is refused.

Moves on when: the suite is rewritten and reviewed again.

workers

Who may touch what

The workers are separate agents with separate tool lists. The point is separation: the author of a suite never sees product code, the judge never sees the builder's notes, and the reviewer edits nothing.

gusthe generator

Writes and edits one AC's suite from the contract, the canonical and the confirmed examples.

Never reads product code. Each suite version waits for rex.

rexthe reviewer

Reviews every suite version, the shape, the diff of each item, and every full run whatever its result. Writes the Attention section of the evidence README.

Never edits suites, code or results.

edthe engineer

Builds test-first on branches of the declared product repo, records builds, fixes red ACs, and diagnoses runs that never reached the product.

Never edits suites, and never merges to trunk without a verdict. Pushes and deploys only through a declared lane.

evethe executor

Runs the reviewed suites through the drivers, records what came back, then scores.

Never judges, edits or builds.

timthe triager

Judges each case's rule checks against its transcript and writes a bug report for every failing case.

Blind to the builder's notes.

dorathe doc author

Drafts the sponsor-facing handover documents as local files, in the pack's language and the roles' words.

Never signs, sends or uploads.

fence

The fence and the ladder

The fence is a hook on tool calls. In any project that has greenfield/fence.yaml it enforces an always-pause list of eleven entries, and everywhere else it stays silent. It also asks before gp accept-line, gp pack accept and gp number, because accepting and issuing are the owner's.

The pack holds the company-specific rules, so the core stays generic. Its hash is recorded in fence.yaml. If a pack file is edited, every non-read tool call asks until the owner runs gp pack accept. A pack rule that loosens the core fence is rejected; the fence takes the union.

Environments are declared in environments.yaml. Production is never listed. A local one must be loopback, a remote one must be in the fence's remote_hosts, and credential names are checked but values never are.

The ladder is the owner's dial for how much runs unattended, per part. hitl makes a part's items wait for the owner and be worked live; afk is the default. A spoken change lasts one session and is logged. It cannot loosen a permanent hitl, and no level ever reaches the fence.

The ceiling is a budget: in fence.yaml: full runs with no newly passing case on one AC, builds, and a deadline. Reaching one raises a ready-for-human item and gp run and gp build refuse.

what the fence is not

It matches regular expressions on command text and tool names. It is conservative and it is not a sandbox. Secret matching is pattern-based and misses what it does not know.

The hook has not yet been loaded by a live Claude Code session. The tests drive it by stdin, so check that it loads before trusting a project to it.

pitch

The second plugin

The same repository holds pitch, which takes a foggy idea, often one discovery note or one sentence, to a won deal. It needs gp and the fence from this plugin, so every artifact is a draft by enforcement.

  • problem-to-solution: chart a map of decision tickets, work them one at a time, compile the Solution Statement, hand off at the win.
  • deal-factor: research the buying committee, criteria, competitors and risks. Findings are sourced.
  • business-proposal and pitch-deck: drafted from the statement.
  • proof-of-concept: the smallest working demo of the named proof requirements.
  • retro: propose small changes to the pack after a finished deal.

The Solution Statement is the only interface between the pitch skills. Pricing, timeline, team and terms in the proposal are left as human inputs, never derived.

status

What is proven, and what is not

Version 0.1.0. Built on three fictional fixtures, with no real project behind it yet.

Shown so far

  • 451 tests passed on the day this page was written (2026-11-25), Windows 11, Python 3.13.
  • Three fixtures (acme-linkr, acme-csv, acme-freight) each go from skeleton to red on every AC, a reference build, green, reviewed, and done.
  • An independence check plants a blind spot that the builder's own tests miss, and the full run turns that AC red.
  • The agent and skill files are tested for structure: tool limits, line caps, and that every gp command they name exists.

Not shown yet

  • A real project. One small real tool, chosen by the owner, has to pass before this is called proven.
  • A live end-to-end run of the workers. The tests check structure, not how a model behaves on the files.
  • Whether a hidden business rule surfaces before the build when a simulated sponsor answers questions, run three times.
  • The container runner on a machine with a runtime, the browser driver, and mobile, desktop or embedded surfaces.
  • The hook in a live Claude Code session, and the unattended ladder level, which is specified but not built.

try it

Run the engine

The engine runs on its own, with no Claude Code needed.

python bin/gp init my-project
python bin/gp doctor
python -m pytest -q

On Windows, use bin\gp.cmd. It needs Python 3.10 or newer, PyYAML and git. Tested only on Windows 11 with Python 3.13 and git 2.55; Python 3.10 to 3.12, Linux and macOS are untested.

As a Claude Code plugin, the repository root is also a local marketplace. Add it with /plugin marketplace add <path to this folder>, then /plugin install greenfield-pipeline@greenfield-pipeline-local. This path has not been tried in a live session.
